# КЛАРА: ПОЛНОЕ ТЕХНИЧЕСКОЕ ЗАДАНИЕ — PACO DEPLOY KIT
Дата исходного среза: 2026-10-31. Язык всей документации и инструкций: русский.

## Роль и цель
Ты — независимый инженер Linux/маршрутизации/VPN и ревьюер. На основании файлов **этого архива** подготовь **реально пригодный к запуску, но НЕ запускаемый тобой комплект Bash-скриптов** для двух вариантов каскадного AmneziaWG. Итог нужен для последующего использования, не только техническое заключение.

- **A / EXIT replacement:** существующая ENTRY Москва остаётся без перевыпуска клиентов; меняем только EXIT на новый пустой VPS в другой локации.
- **B / Two new VPS:** два новых VPS на одинаковой подтверждённой версии Ubuntu; полный каскад с нуля. Подварианты — перенос идентичностей/peer из частных бэкапов или полностью новые ключи/клиенты.

**Целевая сеть:** Клиент AWG → ENTRY awg0 (10.77.77.1/24, UDP 60333) → ENTRY awg1 (10.88.88.1/30, UDP 60334) → EXIT awg1 (10.88.88.2/30) → EXIT WAN SNAT → Интернет. Полный клиентский туннель, без split routing. ENTRY policy table 100 + unreachable fallback + независимый FORWARD DROP (awg0 не через awg1). **Не добавляй OpenVPN, двойной NAT на ENTRY, новый VPN-стек или универсальный firewall flush**.

## Строгое правило доверия
Ни одного приватного ключа / PSK / токена / пароля ни в запросе, ни в ответе, ни в логах. Ключи генерируются локально на VPS после явного согласования; наружу передаются лишь публичные ключи. Любые архивы с клиентскими конфигами, SSH-ключами и SQLite остаются у оператора. Не копировать детали из других проектов (в т.ч. Москва–Хельсинки или HTD). Различай **подтверждено / историческое / предположение / проверить на новом VPS**.

## Данные — из приложенных файлов, без догадок
Изучи `02_PACO_AS_BUILT_CONFIRMED.md`, `05_MOSCOW_AUDIT_ACTUAL_20261031.txt`, `06_EXIT_KNOWN_STATE_AND_GAPS.md`, `09_MANAGER_AND_BACKUPS.md`, оба inventory. Никаких неизвестных WAN-интерфейсов или новых публичных IP не выдумывай. Для отсутствующих значений используй шаблонные переменные и требуй preflight-валидацию на VPS.

Версию AWG/пакетов/написание параметров для конкретной Ubuntu проверь по актуальной официальной документации и реальным пакетам до кодирования установки. Для новых VPS на одном релизе ОС должны быть проверены архитектура, ядро, модули/пользовательская реализация AmneziaWG и firewall backend. При несовместимости — блокировать `--apply` с явной ошибкой; не маскировать ошибки.

## Требования ко ВСЕМ скриптам
1. По умолчанию `--dry-run` без системных изменений. Единственный путь внесения изменений — `--apply` + подтверждение понятного плана действия; никакого скрытого `enable`, `reboot` или `ufw reload` на preview.
2. Каждое применение: root-check, preflight, проверка интерфейсов/подсетей/портов/доступа, отсутствие конфликтующих служб и конкурирующего маршрута; директории 0700, приватные файлы 0600, бэкап в каталог с точным timestamp, фиксированный журнал **без секретов**, атомарная запись файлов.
3. Должна быть **идемпотентность**: повторный запуск не создаёт дубликаты `ip rule`, NAT, UFW, iptables и peer. Разделяй staging и final cutover.
4. Изменения на рабочей ENTRY в сценарии A только после `--apply` и отдельного согласия оператора. Сначала консоль провайдера/второй SSH, затем **временный автоматический rollback** для опасных изменений firewall/маршрутов, проверка и только после неё снятие страховки.
5. Никогда не вызывай `iptables -F`, не меняй хостовый default route, не отключай глобально IPv6/SSH/UFW вслепую; не перезапускай `awg0` при подмене EXIT. При необходимости `awg syncconf` применять ограниченно, с валидацией конфигурации и двухсторонним rollback.
6. Выбор firewall backend должен быть явным и безопасным: ENTRY установлен iptables/netfilter-persistent; EXIT на историческом хосте использует UFW. На **новых** VPS предложи конкретную согласованную реализацию по проверенной ОС, избегай конфликта nft/iptables/UFW. При UFW сначала `iptables-restore --test` и проверка синтаксиса before.rules, затем безопасная загрузка.
7. При потере AWG1, его default route, unit или endpoint клиентский трафик не должен выходить через ENTRY WAN: client `ip rule` должен существовать **независимо** от awg1, таблица с permanent unreachable fallback должна оставаться, и firewall drop `-i awg0 -s <CLIENT_CIDR> ! -o awg1 -j DROP` сохраняться после reboot. Не допускать скрытого fallback в `main` route. Правила должны работать и при неуспешном `awg1` startup; проверить порядок systemd зависимостей.
8. Сопутствующая клиентская IPv6-политика: явно reject/block IPv6 leak либо правильно маршрутизировать IPv6 через EXIT; не ломая удалённый SSH сервера. Если поддержка не реализована — пометить как ограничение и запретить `--apply` при невозможности безопасной реализации.
9. EXIT: отсутствие конфликтующего `awg0` с клиентской подсетью, IP forwarding, обратный маршрут `CLIENT_CIDR dev awg1`, точечное разрешение UDP/60334 **только с ENTRY**, UFW FORWARD (awg1→WAN) и stateful return, MASQUERADE **только для клиентской сети**; не включай SNAT `10.88.88.1` ради Dante — SOCKS не входит в задачу.
10. Для сценария A: новый EXIT должен быть подготавливаем и максимально проверяем ДО переключения. Для проверки полного межсерверного handshake может потребоваться отдельный временный тестовый peer/interface/порт; нельзя обещать, что handshake нового EXIT получится без изменения активного peer ENTRY. Переключение строго с коротким атомарным шагом, контролем firewall whitelist, возвратом к старому EXIT при отказе. Старый EXIT сохранять до завершения.
11. Для сценария B: сохранить клиентские идентичности возможно **только** при восстановлении исходных серверных ключей и peer-данных из защищённого бэкапа. При новом публичном IP ENTRY клиентский `Endpoint` нужно изменить (или обеспечить прежнее DNS/адресное соответствие). Если ключей нет, создание новых профилей и явная раздача; нельзя обещать бесшовный перенос.
12. Обособленный менеджер `paco-awg v0.2.4` и `paco-awg-traffic.timer` не переписывать. При сценарии A они остаются на ENTRY. При B восстановить лишь в согласованном режиме, сохранив историю SQLite, приватные файлы и корректный `ENDPOINT` в самом скрипте (проверить известные жёстко заданные значения). Клиентские параметры: `MTU=1380`, `Jc=5`, `Jmin=10`, `Jmax=50`, `S1=S2=S3=S4=12`, `H1=1`, `H2=2`, `H3=3`, `H4=4` — **проверенные на тестовом профиле PACO**, но на новых версиях/настройках требуют сопоставления.
13. Развертывание должно быть безопасно остановить до каждой опасной точки, а `rollback.sh` должен восстанавливать ключевые правила и состояние без потери доступа. Ни одна команда rollback не должна автоматически удалять действующих клиентов.
14. Все команды должны работать на выбранной проверенной Ubuntu. `bash -n`, `shellcheck` (если установлен), проверка синтаксиса units (`systemd-analyze verify`) и policy/NAT/route-checks — оформить результаты или честно отметить, что тестировалось только статически.

## Тестирование и приемка
- Нет утечек: при отключении основного маршрута AWG1 `ip route get ... from CLIENT_IP iif awg0` даёт unreachable; независимый firewall DROP запрещает выход через WAN.
- Нормальный маршрут идёт через awg1, на EXIT клиентская сеть возвращается через awg1, в WAN применяется SNAT.
- С тестового клиента внешний IP = **текущий публичный IP EXIT**; DNS и HTTPS открываются; старые клиенты в A не требуют нового профиля.
- Порядок reboot: сперва EXIT, затем ENTRY; проверки после каждого, с контролем SSH/консоли. Не перезагружать автоматически.
- Отдельно анализировать: нет handshake, есть handshake нет интернета, отсутствует обратный маршрут/маскарадинг, UFW блокирует forward, конфликт подсетей, default route leak, IPv6, отсутствие AWG0 при старте, недоступен SSH.
- Дать оператору команды сравнения состояния ДО/ПОСЛЕ, критерии GO / NO-GO, процедуру снятия rollback-таймера, процедуру забора внешнего бэкапа.

## Порядок ответа
1. Сначала независимый аудит нашего исходного пакета и критические замечания; не перепроектируй без причины.
2. Затем **весь комплект A и B**, с исходниками скриптов в ZIP, README и тестами. Пользователь просит именно готовые сценарии — не ограничивайся обзором, дополнительными вопросами и pseudocode.
3. Отметь неизвестные поля `TO_CONFIRM`, внешние зависимости, необходимость тестового VPS и результаты валидации. Не заявляй о проверке на VPS, если её не было.
4. Не обращайся к рабочим VPS и не запускай команды от имени пользователя. Предоставь код для проверки Кирой и оператором; применение возможно только после явного согласия.
