# PACO-DEPLOY — независимый аудит Киры и порядок работ

31.10.2026. Исходный архив: `PACO-DEPLOY_20261031.zip` (74 записи).

**Решение:** пригоден для дальнейшей лабораторной проверки после исправлений; пока **NO-GO на рабочей Москве**. Это не проверенный production installer.

## Проверено независимо

- ZIP читается, CRC корректен.
- Корневые SHA256SUMS: 73 записи, 73 OK.
- `bash -n` всех `.sh` — без ошибок.
- `tests/test_offline.py` в текущей среде: 37 тестов, 35 успешных и 2 пропущенных (проверка root-gate и реальный AWG pubkey tool).
- `tests/check_units.py`: PASS только в синтетических unit fixtures, не на действующем systemd графе.
- ShellCheck отсутствует в среде повторной проверки; лог Клары заявляет PASS, независимо не повторялось.
- Действующие VPS не опрашивались и не изменялись при данном аудите. AWG/NAT, возврат трафика и rollback при реальном сбое не проверялись.

## Основные замечания

### P1: возможный цикл systemd в A — исправить до apply

`common/engine.sh` строки 109–116 создают `paco-deploy-guard.service` со связями `After=... paco-failclosed.service` и `Before=network-pre.target`. У текущего московского `paco-failclosed.service` ранее наблюдалось `After=network-online.target`. Стандартный сетевой менеджер упорядочен после `network-pre.target`. Из-за этого при реальной загрузке возможно циклическое упорядочение; локальные fixtures в `tests/check_units.py` не воспроизводят реальные зависимости.

**Требуемое исправление:** развести единицы A и B. В A не требовать guard до `network-pre.target`, если он обязан следовать за legacy-службой после `network-online.target`; обеспечить guard до `awg-quick@awg0/awg1`, предварительно проверить `systemd-analyze verify` с реальным графом и reboot в лаборатории. Не ослаблять fail-closed.

### P1: потеря имён клиентов B restore — подтверждена офлайн

`common/data.py` строки 183–200 в `parse_awg()` удаляют `#` комментарии; `render()` (245–246) не восстанавливает их. `restore_clients()` (248–273) использует эти функции, а B-клиенты записываются через `render()` в `common/engine.sh` (257–295). Поэтому клиентские `# galt`, `# testpaco` и прочие имена исчезают, хотя ключи/AllowedIPs остаются. Проверено синтетическим текстом.

**Требуемое исправление:** сохранить имена в исходной AWG-конфигурации или в проверенном реестре `имя ↔ PublicKey ↔ IPv4` со сверкой и восстановлением комментариев в выходной конфигурации; добавить unit-test на реальный формат именных peer-комментариев.

### Предусловия и ограничения, не баги

- A может остановиться на строгой проверке `ExecStart` старого `awg-quick@awg1.service`: реальная Москва пока не подтверждена на соответствие абсолютному пути `/etc/amnezia/awg1.conf` (см. `docs/RUNBOOK_A.md`). Не менять unit вслепую.
- AWG версии/точный transit-профиль действующего AWG1, PSK и новые public IP/интерфейсы остаются неизученными. Заполнять после read-only аудита, не придумывать.
- Клиентский native IPv6 требует доказанного захвата `::/0` или OS-level block: серверный DROP не защищает от локального IPv6 обхода.
- B не активирует старый PACO Manager v0.2.4 и SQLite collector — `RESTORE_OFFLINE` лишь сохраняет их в карантин. Нужна самостоятельная проверка и установка.
- При новом ENTRY IP нужно обновить `Endpoint` во всех клиентских профилях (или заранее спроектировать стабильное DNS-имя). Перенос приватного ключа входного сервера не сохраняет старый public endpoint.
- Клиент `client01` не имеет сохранённого `client01.conf`; его приватный ключ из сервера нельзя восстановить.
- Временной rollback timer (300–3600 с) не является гарантией мгновенного/успешного rollback; следить за deadline, иметь console и внешний backup.
- В тестах сетевого fail-closed, reboot, SSH whitelist, FW NAT, клиентского IP нет реальных проверок; все эти проверки обязательны в отдельной лаборатории.

## Предлагаемая последовательность действий

### Общий этап 0 — ничего не меняем на PACO

1. Получить у Клары исправления для двух P1 с повторными offline-тестами.
2. В лаборатории поднять два новых VPS Ubuntu 24.04 одинакового точного релиза (желательно один провайдерский снимок ОС), доступ по консоли и двум SSH-сеансам.
3. Сверить WAN public IPv4, WAN IF, ядро, архитектуру amd64, доступный диск и RAM, iptables backend, provider firewall, AWG версии/доступность подписанных пакетов.
4. На каждом узле создать собственные root-only `config.env` и `inventory.env` с реально измеренными значениями; ключи и PSK только локально.
5. Подтвердить IPv6-политику и доступность внешнего backup.

### Сценарий A — меняется только EXIT, Москва сохраняется

1. Пройти read-only аудит текущей Москвы AWG1/units/hooks, транзитного профиля/ключей, SSH и fail-closed. Не изменять AWG0, клиента или менеджер.
2. На новом EXIT установить AWG из согласованного источника/версии (скрипт `common/install-awg.sh`), создать ключи (`common/generate-transit-identity.sh`); перенести только public keys в оба inventory.
3. В лаборатории подготовить новый EXIT: `scenario-A/01-prepare-new-exit.sh` с обязательным dry-run → после разрешения apply. Проверить NAT и обратный маршрут; старый EXIT оставить работающим.
4. Назначить окно переключения, достаточный rollback deadline, открыть консоль и две SSH сессии. На Москве проверить `scenario-A/02-stage-and-switch-entry.sh --dry-run`, затем отдельно согласовать `--apply`.
5. Проверить transit handshake, трафик всех видов с тестового клиента, новый внешний IP EXIT, DNS/HTTPS, fail-closed (route loss + awg1 stop), native IPv6.
6. Перезагрузить EXIT и ENTRY по очереди в лаборатории, повторить проверки.
7. Заполнить подлинный operator acceptance, commit на обоих VPS (`scenario-A/03-verify-and-commit.sh`), затем сохранить новые внешние бэкапы. При ошибке сначала откатить московскую ENTRY на прежний EXIT, потом разбирать новый EXIT.

### Сценарий B — две новые локации

1. На двух НОВЫХ VPS заполнить отдельные inventories и выбрать `RESTORE_FROM_OWNER_BACKUP` или `REISSUE_ALL`. Проверить, что клиентский `Endpoint` указывает на новый ENTRY IP:60333.
2. Проверить версии и выполнить `common/install-awg.sh` на обоих; создать локальные AWG1 keys и обменяться только public keys.
3. Выбрать один transit profile AWG1 на оба узла (не копировать вслепую с AWG0), проверить поддержку S1–S4/headers и kernel round-trip.
4. Настроить новый EXIT через `scenario-B/01-setup-exit.sh`, затем ENTRY через `scenario-B/02-setup-entry.sh`. До клиентского AWG0 должна быть независимая защита и возвратный путь.
5. Проверить туннель командой `scenario-B/03-connect-servers.sh`.
6. Восстановить идентичности/клиентов или выдать один новый тестовый профиль через `scenario-B/04-restore-clients-or-enroll.sh`. При restore обязательно восстановить имена клиентов и вручную проверить соответствие старых профилей новому Endpoint. Запуск менеджера/истории только после отдельной адаптации.
7. Провести все сетевые, IPv6, fault/reboot/SSH tests в лаборатории, затем `scenario-B/05-verify-and-commit.sh` на обоих. После успешной приёмки тестового клиента распространять остальные профили.

### Предпросмотр перед любым apply

Пример, находясь в каталоге `PACO-DEPLOY` на соответствующем узле и только при наличии реальных root-only inventory/config:

```bash
bash scenario-A/02-stage-and-switch-entry.sh \
  --config /root/paco/config.env --inventory /root/paco/inventory.env --dry-run
```

`--dry-run` не означает, что сеть уже подготовлена; `NO-GO` при неизвестном поле — ожидаемая безопасная остановка. `--apply` выполнять только по отдельно одобренному runbook после устранения двух P1 и лабораторной проверки.

## Краткое поручение Кларе

Исправить `paco-deploy-guard.service` ordering для действующей ENTRY A с реальным `paco-failclosed.service After=network-online.target`; проверить отсутствие cycle и сохранение fail-closed до AWG0. В сценарии B restore сохранить/восстановить `# имя` каждого Peer при парсинге/рендеринге `awg0.conf`; добавить regression-test. Дать новый ZIP, changelog, повторить static tests; не заявлять TESTED IN LAB без VPS тестов.
